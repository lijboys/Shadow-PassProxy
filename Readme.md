# HTTP重定向（301/302）与反向代理区别指南

## 简介
301/302重定向和反向代理是Web服务中常用的流量控制手段，但三者的**工作原理**、**客户端感知**和**适用场景**差异显著。本文档详细解析其核心区别、适用场景及配置示例，帮助开发者快速选型。


## 1. 核心概念详解

### 1.1 301 永久重定向（301 Moved Permanently）
- **定义**：资源**永久**移动到新URL，浏览器和搜索引擎会长期记住该重定向。
- **关键特点**：
  - HTTP状态码：`301`
  - 缓存行为：浏览器**长期缓存**（需手动清除缓存才能失效）
  - SEO影响：搜索引擎将旧URL的权重**完全转移**到新URL，并更新索引

### 1.2 302 临时重定向（302 Found / Moved Temporarily）
- **定义**：资源**临时**移动到新URL，未来可能恢复原URL。
- **关键特点**：
  - HTTP状态码：`302`（HTTP/1.1推荐用`303`/`307`更规范）
  - 缓存行为：默认**不缓存**（除非响应头明确指定`Cache-Control`）
  - SEO影响：搜索引擎**保留旧URL索引**，不转移权重

### 1.3 反向代理（Reverse Proxy）
- **定义**：代理服务器接收客户端请求，转发给后端真实服务器，再将结果返回客户端。客户端**感知不到真实服务器存在**。
- **关键特点**：
  - 无特定状态码（正常转发返回`200`/`404`等）
  - URL表现：客户端URL**不变**（仍为代理服务器地址）
  - 核心作用：负载均衡、安全防护、缓存加速、SSL终端等


## 2. 核心区别对比表

| 维度                | 301 永久重定向                | 302 临时重定向                | 反向代理                      |
|---------------------|-------------------------------|-------------------------------|-------------------------------|
| **HTTP状态码**      | 301                           | 302（或303/307）             | 无特定（通常200/404等）      |
| **资源移动性质**    | 永久                          | 临时                          | 不移动，代理转发              |
| **客户端URL变化**   | 变为新URL                     | 变为新URL                     | 不变（仍为代理URL）           |
| **浏览器缓存**      | 长期缓存                      | 默认不缓存                    | 可缓存静态资源（视配置）      |
| **SEO处理**         | 权重转移，更新索引            | 保留旧索引，不转移权重        | 无直接影响（代理URL参与索引） |
| **客户端感知**      | 知道资源移动                  | 知道资源临时移动              | 不知道真实服务器存在          |
| **主要作用**        | URL变更、权重转移             | 临时跳转、A/B测试             | 负载均衡、安全防护、缓存加速  |
| **性能影响**        | 首次重定向后缓存，后续无开销  | 每次请求都可能重定向          | 增加代理层开销，但可优化整体  |


## 3. 适用场景详解

### 3.1 301 永久重定向适用场景
- **域名变更**：旧域名废弃，永久切换到新域名（如 `old.com` → `new.com`）
- **URL规范化**：非www域名重定向到www（或反之），如 `example.com` → `www.example.com`
- **HTTP→HTTPS**：网站升级HTTPS，永久重定向HTTP请求到HTTPS
- **内容永久整合**：旧内容删除，重定向到相关新内容或首页

### 3.2 302 临时重定向适用场景
- **网站临时维护**：将用户临时跳转到维护页面，维护结束后恢复
- **A/B测试**：临时将部分用户跳转到测试页面，收集数据
- **临时活动跳转**：活动页面临时上线，结束后恢复原页面
- **地理位置临时跳转**：根据用户IP临时跳转到地区页面（非永久策略）

### 3.3 反向代理适用场景
- **负载均衡**：将请求分发到多台后端服务器，提升并发能力（如Nginx代理到多个Tomcat）
- **安全防护**：隐藏后端服务器真实IP，防止直接攻击，可搭配WAF
- **SSL终端**：在代理服务器处理SSL加密/解密，后端只需处理HTTP
- **静态资源缓存**：代理缓存图片、CSS等静态资源，减轻后端压力
- **跨域解决**：前端请求代理服务器，由代理转发到后端API，避免跨域
- **统一服务入口**：多个服务通过同一域名的不同路径访问（如 `example.com/api` → API服务，`example.com/web` → Web服务）


## 4. 注意事项

### 4.1 301重定向注意事项
- **谨慎使用**：浏览器长期缓存301，配置错误需用户清除缓存才能恢复
- **避免链式重定向**：不要 `A→B→C`，直接 `A→C`，减少性能损耗
- **确认永久变更**：若未来可能恢复，用302而非301

### 4.2 302重定向注意事项
- **避免滥用影响SEO**：长期用302可能被搜索引擎视为作弊，永久变更请用301
- **HTTP版本兼容**：HTTP/1.1中，`303`（POST转GET）和`307`（保持请求方法）更规范
- **明确缓存策略**：若需缓存302，需添加 `Cache-Control` 响应头

### 4.3 反向代理注意事项
- **配置转发头**：添加 `X-Forwarded-For`（真实客户端IP）、`X-Forwarded-Proto`（真实协议），让后端获取正确信息
- **避免单点故障**：代理服务器需高可用，可部署多台做HA（高可用）
- **性能优化**：合理配置缓存、连接池，减少代理层开销
- **安全配置**：限制代理访问权限，防止被滥用为开放代理


## 5. 示例配置（Nginx）

### 5.1 301永久重定向配置
```nginx
# 旧域名→新域名
server {
    listen 80;
    server_name old.com www.old.com;
    return 301 https://new.com$request_uri;
}

# HTTP→HTTPS
server {
    listen 80;
    server_name example.com www.example.com;
    return 301 https://$server_name$request_uri;
}
```

### 5.2 302临时重定向配置
```nginx
server {
    listen 80;
    server_name example.com;
    # 临时跳转到维护页面
    return 302 https://example.com/maintenance.html;
}
```

### 5.3 反向代理配置
```nginx
upstream backend {
    server 127.0.0.1:8080;  # 后端服务器1
    server 127.0.0.1:8081;  # 后端服务器2（负载均衡）
}

server {
    listen 80;
    server_name example.com;

    # 转发动态请求到后端
    location / {
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # 静态资源缓存
    location /static/ {
        proxy_pass http://backend;
        proxy_cache_valid 200 1d;  # 缓存1天
    }
}
```


## 总结
- **301**：用于**永久变更**，侧重SEO权重转移
- **302**：用于**临时跳转**，侧重短期流量调度
- **反向代理**：用于**服务架构优化**，侧重负载均衡、安全和性能

根据业务需求选择合适的技术，避免混用导致的SEO或性能问题。
